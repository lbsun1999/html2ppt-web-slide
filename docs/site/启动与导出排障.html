Windows启动与PDF／PPTX导出#

自选导出路径#

在本地工作台点击PDF或PPTX，支持文件系统访问的Chrome／Edge会先显示保存位置选择框，再生成文件。可取消而不启动生成；生成失败不覆盖已存在的目标文件。浏览器不支持该接口时使用下载，可在浏览器下载设置中开启“每次询问保存位置”。离线HTML仍先传送当前文稿到本地工作台，再选择导出位置。

直接打开HTML可以编辑、保存和放映。PDF／PPTX由本机Node.js服务生成，因此需要先启动服务；把文件拖到仍是file:///的离线页面，不会自动启动服务。

推荐流程：自动传送，不需要拖拽#

  1. 将完整项目ZIP解压到本地文件夹，保留package.json、scripts、src等文件。安装Node.js 20.10+和Chrome／Edge。
  2. 双击启动.cmd。首次运行会恢复锁定的依赖；看到“服务已就绪”后保持该窗口开启。
  3. 回到正在编辑的离线HTML，点击“导出PDF／PPTX”，在弹窗点击“传送当前文稿”。当前内容连同尚未保存的修改会载入新工作台窗口。
  4. 在新窗口点击对应的导出按钮。也可直接访问http://127.0.0.1:4317，点击“打开HTML”选择文稿，使用文件选择器代替拖拽。

传送只允许http://127.0.0.1:端口或http://localhost:端口，通过新窗口消息交换结构化文稿，内容不传到外部网站。页面与随机令牌绑定，传送后移除URL中的临时令牌。原窗口继续保留修改；导出文件是当前内容的快照。

双击启动失败：在终端中运行#

在项目文件夹的资源管理器地址栏输入powershell并回车，然后执行：

node scripts/start.mjs --open

无需管理员权限。也可以先做环境检查：

node scripts/start.mjs --check

若希望直接调用原服务，可执行node server.mjs，随后手动打开工作台地址。使用npm.cmd start也会调用新的启动器；Windows下明确使用.cmd，避免终端将npm解析为受执行策略限制的npm.ps1。

启动日志保存在ect/startup.log，包含Node版本、依赖检查及服务输出。报错时提供日志末尾的错误信息；没有日志通常意味着启动器尚未执行，应先核对文件是否完整、Node是否安装、文件是否被系统拦截。

“这些文件可能对你的计算机有害”#

若提示“你的Internet安全设置表示一个或多个文件可能有害”，先核对文件是否来自预期的项目下载。Windows会给下载文件附加Internet来源标记（Mark of the Web），该标记可能在打开、拖放或启动时触发安全提醒；提示本身不能用来判断文件已经被检出恶意软件。Microsoft对附件管理器的说明。

对于已核对来源的本项目文件，可以右键文件→“属性”→“常规”，查看底部是否有“解除锁定／取消阻止”；存在时勾选后应用。若是下载ZIP，可在解压前对可信ZIP检查此属性，再重新完整解压。仅处理已确认的文件，不需要关闭Defender、SmartScreen或放宽整台电脑的安全策略。

拖拽仍被阻止时，使用上面的“传送当前文稿”，或工作台的“打开HTML”按钮。若安全中心明确给出威胁名称、隔离记录或组织策略，则保留具体提示并进一步核实，不要将所有安全拦截都当作文件来源提醒处理。

旧版“确认后闪退”的已知原因#

2026-10-26在实际Windows环境复现：旧ZIP中的启动.cmd是LF换行，CMD解析时出现命令被截断、中文被当成命令等错误，服务未启动。修复后的入口采用纯ASCII及CRLF换行，中文检查和日志交给Node.js。

仓库对*.cmd使用-text保留实际CRLF字节，保证GitHub源码ZIP与发布包中的批处理也正确。仅设置text eol=crlf会转换检出工作区，Git归档仍可能输出规范化后的LF；维护发布时必须检查ZIP内的真实字节。可参考Microsoft的Windows批处理换行约定。

此原因已在本机复现和修复，不代表所有闪退都由换行造成；其余问题以日志为准。
